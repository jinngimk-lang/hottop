# Latent Spatial Memory admission review — 2026-08-28

## Why this candidate matters

Production v0.2's remaining generated-video gap is not provider count; it is **real subject/scene continuity across multiple shots and viewpoints**. Microsoft `LatentSpatialMemory` is relevant because it stores persistent 3D scene state directly in latent tokens and updates that memory across generated chunks, avoiding an explicit RGB render → re-encode detour.

Reviewed source:

- repository: `microsoft/LatentSpatialMemory`
- exact reviewed revision: `be530516a8b8c79ae5d5dff543b4d1640f59bd54`
- revision date: 2026-08-27
- code license: MIT (`LICENSE` present at the reviewed revision)
- public base path in README: Wan2.2-TI2V-5B plus VACE/LoRA-style training/inference assets

## Mechanism relevance

The published design maintains persistent scene content as latent memory with an explicit lifecycle:

1. initialize memory from the starting observation;
2. read target-view memory for the current chunk;
3. use memory during denoising;
4. write updated static scene content back into the cache.

This is complementary to ReWorld's bounded recent-cache + pose-indexed landmark-bank idea. ReWorld emphasizes bounded retrieval of old viewpoints; Latent Spatial Memory emphasizes keeping persistent 3D scene state in latent space rather than repeatedly materializing and re-encoding RGB/3D caches.

For Hottop, both mechanisms are relevant to scene geography and long-horizon viewpoint consistency. Neither architecture claim is itself evidence that a generated Odyssey sequence preserves identity.

## Admission decision

**Decision: permissive research/benchmark candidate; no production route yet.**

The source code clears the code-license layer, but the executable production gate is not cleared:

1. **Code license is clear:** exact reviewed source includes an MIT license.
2. **Runtime remains operator-owned:** upstream requires a Python/PyTorch environment and separately provisioned Wan2.2-TI2V-5B assets; Hottop must not auto-provision those resources.
3. **Trained project assets are not independently admitted:** the README's inference example expects project-specific `vace.safetensors` and `lora.safetensors` paths. At this review, Hottop has no independently verified published checkpoint revision/rights record for those trained assets.
4. **Base/model rights are separate:** Wan2.2 model/checkpoint rights, any Latent Spatial Memory trained weights, reference-image rights and output/publication rights must be reviewed independently from the MIT source license.
5. **No hidden download path:** Hottop must not add a normal `video-run` route until exact local source/model paths can be preflighted without implicit multi-GB downloads.
6. **No quality claim without real output:** efficiency numbers or paper metrics do not replace Hottop's subject-bound continuity evaluator and byte/provenance gates.

## Re-admission / integration gate

Re-evaluate for a narrow operator-owned adapter only when all of the following are true:

1. exact project-specific inference checkpoint revisions and their licenses/rights are independently verifiable;
2. an operator has already provisioned the local source, base Wan2.2 assets and required trained weights;
3. the route can run offline after preflight;
4. a rights-safe Odyssey reference pack exists;
5. at least two subject-bearing shots can be generated from the same subject sequence;
6. every accepted shot passes motion/decodability, exact-byte provenance and final-media gates;
7. continuity evidence covers all subject-bearing shots and binds evaluator revision, exact reference bytes, exact generated bytes, generator source revision and model/checkpoint revision where independently verifiable;
8. the route produces a measurable continuity/scene-memory gain over the current tested LightX2V/Wan2.2 benchmark route.

## What may be reused now

Because the code is MIT, a future implementation may directly reuse compatible source under its license if there is concrete measured value and dependency/runtime cost is justified. **Do not vendor the project wholesale.** Prefer a narrow adapter or selectively port only the minimum memory behavior needed by an admitted local route.

Until trained checkpoint provenance and operator runtime exist, keep this candidate out of unattended execution and treat it as a promising scene-memory mechanism rather than a production backend.
