# Wan2.2 SDNQ operator candidate — 2026-09-01

## Measured gap

Production v0.2 still lacks operator-provisioned real Wan2.2 I2V evidence in the current execution environment. A materially lower-memory local route could reduce the hardware threshold, but only if code, weights, runtime behavior and generated-content quality remain reviewable and zero-paid.

## Candidate

- Runtime/code: `Disty0/sdnq` exact public `main@06c83b3878d7240da5d8b8c94ae798af9a047e6b`, package version `0.2.7`.
- Code license: **GPL-3.0-only** according to the repository `pyproject.toml` and LICENSE. This is deliberately tracked separately from model licensing and must not be described as Apache-2.0.
- Runtime dependencies declared by the package: `torch`, `diffusers`, `transformers`, `accelerate`. The README says Diffusers `>=0.40.0` has native SDNQ support and documents CUDA/ROCm/XPU/CPU plus fallback device execution, with optional OpenVINO installed separately.
- Candidate weights: `Disty0/Wan2.2-I2V-A14B-SDNQ-uint4-svd-r32`, advertised as a 4-bit UINT4/SVD-rank-32 quantization of `Wan-AI/Wan2.2-I2V-A14B-Diffusers`; the published model card reports **Apache-2.0** for the weights.
- LightX2V issue #700 requests SDNQ 4-bit support, but that issue is a request rather than evidence that the current LightX2V Wan2.2 operator path interoperates correctly with these weights.

## Admission decision

**Gated; do not integrate into unattended Hottop yet.**

Reasons:

1. Code and weights have different licenses. The runtime is GPL-3.0-only while the published quantized weights are Apache-2.0. Hottop must not vendor or copy SDNQ implementation into its permissive/operator adapter surface without a separate compatibility decision.
2. The documented usage installs a runtime package and loads a separately acquired large model. Neither dependency installation nor model acquisition belongs in normal `video-run` or CI under `ZERO_COST_MODE=true`.
3. There is no Hottop same-reference Wan2.2 I2V A/B proving identity fidelity, requested-action motion, temporal stability or cinematic quality relative to the reviewed LightX2V/Wan2.2 path.
4. The public LightX2V request does not establish exact integration/config compatibility, and current LightX2V quality reports already show that successful execution or correct frame counts are insufficient evidence.

Operator-owned private execution of an already-provisioned SDNQ environment may be benchmarked later through a narrow fail-closed external adapter if license review permits that deployment shape. Any such benchmark must remain offline after preflight, bind exact code/runtime/model/config/reference/generated bytes, and reuse Hottop's media, identity and requested-action quality gates.

## Security / network / cost boundary

No SDNQ code or model was installed or downloaded during this review. The candidate's documented `pip install` and `from_pretrained(...)` paths are network-capable provisioning steps, so they remain explicitly operator-owned and outside unattended execution. No hosted API or paid generation route is required by the candidate itself, but zero monetary API cost does not make automatic multi-GB acquisition acceptable.

## Rollback / doctrine impact

This record changes no runtime and requires no rollback beyond deleting the note. `PROJECT.md` remains unchanged: separating code license from weight license, preventing unattended provisioning, and requiring measured same-case quality before candidate admission are already canonical doctrine.
